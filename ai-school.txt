   - Same linter/formatter config and project structure conventions

   Before writing package.json for noteswift-school, open the
   package.json of noteswift-teacher, noteswift-student, and (if present)
   noteswift-parents side by side and carry over matching dependencies
   and versions for anything already in scope. Only add a new dependency
   if the feature genuinely doesn't exist anywhere yet, and even then
   prefer the same ecosystem already in use.

2. Theme: port the exact theme tokens (colors, fonts, radii, shadows,
   spacing, breakpoints) from the existing noteswift apps into
   noteswift-school so every app in the suite is visually one consistent
   design system. If a shared theme/package already exists, consume it
   directly; otherwise copy the theme file(s) byte-for-byte equivalent.
   Do not invent a new palette, do not reuse any color/font from the

   DM Sans usage are NOT the source of truth — they are forbidden as a
   direct copy; only the noteswift app theme is authoritative).

3. Full responsiveness (REQUIRED, explicit deliverable):
   - The app must be fully usable and visually correct across mobile
     (~360–480px), tablet (~600–1024px), laptop (~1024–1440px), and large
     desktop (1440px+) viewports — test and adjust at all of these, don't
     just rely on one breakpoint.
   - Sidebar collapses into a drawer/hamburger pattern on mobile/tablet,
     matching whatever pattern the other noteswift apps already use (or,
     if none exists yet, design one consistent with their theme and
     document the choice for reuse by sibling apps later).
   - All grids (KPI cards, charts, tables, leaderboard, at-risk list,
     etc.) reflow appropriately at each breakpoint — multi-column on
     desktop, single-column stacking on mobile — no horizontal overflow,
     no clipped content, no overlapping elements at any width.
   - Tables that don't fit narrow viewports get a sensible mobile
     treatment (horizontal scroll with a visible scroll affordance, or a
     card-based row layout on small screens) rather than breaking layout.
   - Charts/canvas elements resize correctly on viewport/container resize
     and on orientation change, without becoming blurry or misaligned.
   - Touch targets (buttons, nav items, table action links) meet a
     minimum comfortable tap-size on mobile.

4. Dynamic/fluid text sizing (REQUIRED, explicit deliverable):
   - Use a fluid type scale (e.g. CSS clamp()-based sizes, or a
     responsive typography utility already present in the other
     noteswift apps if one exists — reuse it) so headings, body text,
     stat values, and labels scale smoothly across viewport sizes rather
     than jumping abruptly at breakpoints or staying fixed-size and
     causing overflow/truncation on small screens.
   - Respect user/browser font-size preferences — use relative units
     (rem/em) throughout rather than hardcoded px for font sizes, so the
     app respects OS/browser accessibility zoom and text-size settings.
   - Long content (student names, assignment titles, announcement text)
     must truncate gracefully (ellipsis + full text on hover/tap, or
     wrap) rather than breaking card/table layouts at any text length or
     viewport size.

5. Security measures (REQUIRED, explicit deliverable — frontend-
   appropriate hardening, even though there's no real backend yet):
   - Treat all mock/seeded "user-generated" content (e.g. announcement
     text, message bodies, student/staff names) as untrusted: render via
     framework-safe methods only — never use dangerouslySetInnerHTML /
     innerHTML / v-html or equivalent with unsanitized content; if any
     rich text must be rendered, sanitize it first using a library
     already in the noteswift stack or a well-known sanitizer (e.g.
     DOMPurify) and document the dependency choice.
   - All forms (login, announcement composer, message composer, report
     filters, search) must validate and sanitize input client-side
     (length limits, type checks, no raw script injection vectors)
     before it's used anywhere in the UI, even against mock data.
   - Auth token / session storage must follow the same secure pattern as
     the rest of noteswift (e.g. if they use httpOnly-cookie-style
     patterns or a specific localStorage key convention with expiry
     handling, mirror it exactly) — do not invent a less secure pattern
     just because this is mock-only.
   - Protected routes must hard-fail closed: any route requiring auth
     must never flash protected content before redirecting an
     unauthenticated user (no content flicker, no relying on client-side
     checks alone if a more robust pattern exists elsewhere in the
     stack).
   - No secrets, API keys, or real credentials committed anywhere in the
     codebase, including mock files — only clearly-labeled fake/demo
     values.
   - Add basic security-relevant meta tags / headers groundwork
     consistent with the other apps (e.g. if they set a CSP meta tag,
     referrer-policy, or X-Content-Type-Options via their hosting config,
     mirror the same approach) so this app isn't a weaker link in the
     suite.
   - Avoid exposing internal mock-data implementation details in the UI
     (no console.log of full auth objects/tokens in production build
     paths, no verbose error messages that would leak structure once
     real APIs are wired in — design error states to show user-friendly
     messages now so the pattern is already correct for Phase 2).
   - Rate-limit-style UX groundwork on the login form (disable submit
     button while a mock request is "in flight", basic lockout/backoff
     UI pattern after repeated failed attempts) even though there's no
     real backend yet — this keeps the form ready for real auth
     integration without UX rework later.

6. No functional bugs (REQUIRED, explicit deliverable):
   - Every interactive element (nav links, tabs, filters, search, sort,
     dropdowns, modals, toasts, the school/year/student selectors, report
     buttons, message compose, pagination) must actually work against the
     mock data layer — no dead buttons, no console errors/warnings, no
     broken links, no unhandled promise rejections.
   - All loading, empty, and error states must be implemented for every
     data-driven view (e.g. what the Student Directory looks like with
     zero matching search results, what a chart looks like while
     "loading," what happens if a mock async call is simulated to fail).
   - Manually verify each page at each breakpoint from item 3 before
     considering it done.

6a. Error handling and null/undefined safety (REQUIRED, explicit
    deliverable):
   - Every component that reads from mock/seed data must defensively
     handle missing, null, undefined, or empty values — a student with
     no avatar initials, a class with zero enrolled students, an
     announcement with no recipients yet, a chart with an empty dataset,
     a search/filter with zero matches — none of these should ever throw,
     render "undefined"/"NaN"/"null" as visible text, render a blank
     broken layout, or crash the page. Provide sensible fallback UI
     (placeholder avatar, "No data yet" / "No students match your
     search" empty-state messaging, "—" for missing numeric values,
     skeletons that resolve to empty-state cards rather than infinite
     spinners).
   - Wrap top-level route/page components in error boundaries so a
     failure in one widget (e.g. a chart) degrades gracefully and shows
     a recoverable error message there, without taking down the entire
     dashboard.
   - All mock async functions (in the data-access/service layer) must
     support a simulated failure/error path, and every component calling
     them must handle that path with a real error UI (not just a
     console.error) — this is what will make the Phase-2 swap to a real,
     occasionally-failing API safe and already-tested.
   - Form validation errors (login, announcement composer, message
     composer, settings forms) must be handled per-field with clear,
     specific, professional messaging — never a raw stack trace, raw
     validation-library output, or a generic "Something went wrong" when
     a more specific message is knowable.
   - Numeric/percentage calculations (averages, rates, trends) must guard
     against divide-by-zero and empty-array cases (e.g. a brand-new class
     with no attendance records yet should show "No data" rather than
     "NaN%" or "Infinity%").
   - Network/async timeouts (simulated) must be handled with a retry
     affordance where appropriate, not a silently-stuck loading state.

7. Mock data layer design (important for Phase 2 reuse):
   - Put all mock data in a clearly isolated location, e.g.
     src/mocks/ or src/data/seed/.
   - Shape every mock object to mirror the likely real API response
     shape inferred from noteswift-backend in Step 0 (same field names,
     nesting, casing conventions, pagination envelope if backend uses
     one).
   - Build a thin data-access layer (e.g. src/services/*.ts) that
     currently reads from mocks but is structured so each function's
     internals can be swapped for a real axios/fetch call later without
     changing any component code. Gate mock vs real behind a single
     config flag/env var (e.g. VITE_USE_MOCKS=true), matching whatever
     convention the other noteswift apps already use if one exists.
   - Seed realistically: at least 1 school, 1000+ students isn't
     necessary but seed enough variety (multiple grades/sections,
     dozens of students with varied attendance/score profiles including
     several genuinely "at-risk" ones, multiple teachers, several weeks
     of attendance/performance history, a realistic mix of assignment/
     quiz/mock-test states, several announcements/messages) that every
     page on the nav looks fully populated and convincing, not sparse or
     obviously fake.

8. Routing: protected routes for everything except /login. Sensible
   redirects (logged-out → /login, logged-in hitting /login →
   /dashboard).

9. Accessibility: proper semantic HTML, labelled form fields, keyboard-
   navigable nav/menus/tabs/modals, visible focus states, sufficient
   color contrast within the inherited theme, ARIA attributes where
   native semantics fall short (e.g. tab panels, live regions for
